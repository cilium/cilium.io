Production deployments are rarely sent directly to 100% of traffic. The common pattern is to start
with a small slice, watch a signal, then widen. A `CiliumNetworkPolicy` has no equivalent built-in
rollout stage. Kubernetes distributes it to Cilium agents, and each matching endpoint enforces it as
its policy is regenerated. There is no intentional percentage rollout, analysis window, or promotion
step.

Traffic splitting is the wrong primitive for access control; deterministic selector scope is the
closest safe analogue. Operationally, however, a bad policy can still cause a broad, quiet
application outage.

## Why policy failures are quiet

A bad deployment usually announces itself. Pods crash-loop, error rates spike, the readiness probe
goes red, and something pages.

A denied L3/L4 connection often does not produce a direct process-health signal; it appears as a
silent drop, timeout, retry storm, or circuit-breaker event. That is the documented default. Cilium's
`--policy-deny-response` option describes it plainly: *"Silently drop denied packets. Applications
will experience connection timeouts when policy denies traffic."*

Below the application, the delay has a shape worth knowing. The dropped packets produce TCP SYN
retransmissions, and the client's stack works through its retransmission schedule before anything
surfaces as a failure. The application-level timeout fires last, by default, long after the network
layer knew. Retries make it look like load. Circuit breakers open, and the dashboards blame the
dependency rather than the policy.

Not every denial is silent. Cilium can experimentally return ICMP Destination Unreachable for denied
egress via `--policy-deny-response=icmp`, though the documentation notes this applies only to IPv4
and IPv6 egress pod traffic and that ingress denial is not currently supported. L7 policy violations
can return explicit responses such as HTTP 403 or DNS REFUSED. The quiet case is the L3/L4 default,
which is also the most commonly deployed.

Blast radius is decided by a selector rather than a percentage. In a namespaced
`CiliumNetworkPolicy`, `endpointSelector: {}` selects all endpoints in that namespace. In a
`CiliumClusterwideNetworkPolicy`, an empty selector can have cluster-wide scope. Neither is a
gradual anything.

## Cilium already ships something close to the missing primitive

Here is what makes this interesting rather than just a complaint. Cilium has a mechanism a staged
policy rollout could be built from. It is called Policy Audit Mode, and the
[documentation](https://docs.cilium.io/en/v1.20/security/policy-creation/) describes it plainly:

> Policy Audit Mode configures Cilium to allow all traffic while logging all connections that would
> otherwise be dropped by network policies.

That is close to a dry run for L3/L4 deny behavior, but not for one candidate policy in isolation.
Audit Mode evaluates the effective L3/L4 policy set on audited endpoints, disables enforcement there,
and records would-be drops. It will not tell you that an overbroad policy has newly *allowed*
something it should not have, because nothing was denied to observe.

The workflow it enables is a good one: observe what would be dropped, refine, then enforce.

## Four limitations stop it being a rollout stage

**It audits endpoints, not candidate policies.** The unit of audit is the endpoint, so you cannot ask
"what would this one new policy do?" You can only ask "what would the whole effective policy set do
to these endpoints?"

**It surfaces would-be drops, not unintended new allows.** Half of a policy review is checking that a
change has not widened access. Audit Mode is structurally unable to answer that, since its signal is
generated by denials that no longer happen.

**It covers L3/L4 only.** The documentation scopes it to policies implemented at layers 3 and 4, so
L7 rules are outside what it reports.

**Its durable control is daemon-wide while its granular control is temporary.** This is the one that
decides the matter, and it is worth taking in two parts.

The persistent configuration is daemon-wide. The switch is the `policy-audit-mode` key in the
`cilium-config` ConfigMap, set through the `policyAuditMode` Helm value, which renders straight into
that key:

```yaml
{{- if hasKey .Values "policyAuditMode" }}
  policy-audit-mode: {{ .Values.policyAuditMode | quote }}
{{- end }}
```

Setting it stops enforcement for every endpoint the daemon manages, which the documentation is direct
about:

> When Policy Audit Mode is enabled, no network policy is enforced so this setting is **not
> recommended for production deployment**.

To de-risk one new policy you would stop enforcing all the others.

Per-endpoint audit narrows the blast radius, but every audited endpoint loses enforcement from the
entire effective policy set, not just the candidate policy, and the override resets when its Cilium
agent pod restarts. The documentation says so:

> This approach is meant to be temporary. **Restarting Cilium pod will reset the Policy Audit Mode to
> match the daemon's configuration.**

A rollout stage that silently ends on an agent restart is not one you can build a process on, and the
state is not expressible in the policy manifest at all.

So the ingredients are present and the assembly is not. Audit Mode behaves correctly as the debugging
aid it is documented to be.

## What to do in the meantime

None of this requires waiting for a feature.

**Stage by selector, not by percentage.** Give the rollout its own label and select on it, so
widening exposure is a label change on workloads rather than an edit to the policy itself:

```yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: payments-egress
spec:
  endpointSelector:
    matchLabels:
      app: payments
      rollout-group: canary
```

Label one deployment `rollout-group: canary`, watch it, then add the label to the next tranche. It is
a coarse, deterministic rollout mechanism, but it requires a dedicated rollout label, a pre-apply
endpoint count and list, representative dependency coverage, and validation against the full
effective policy set. Multiple policy types can overlap and deny rules take precedence, so the
candidate policy is never the only thing deciding the outcome.

Give promotion an explicit gate: all intended endpoints matched, policy status valid, and no
unexplained audit or drop verdicts across a representative traffic window.

**Do the audit pass somewhere that is allowed to be unenforced.** Since daemon-wide audit is not for
production, verdict collection belongs in staging with production-shaped traffic, or in a cluster you
are willing to leave unenforced. The verdicts are evidence, not proof. The guide is explicit that the
audit loop is bounded by what you exercised: *"These steps should be repeated for each connection in
the cluster to ensure that the network policy allows all of the expected traffic."* Staging can miss
production-only identities, labels, DNS resolutions, service paths, and traffic. An empty audit log
only means the observed traffic window was clean.

**Instrument the transition, not just the policy.** Record the policy UID, generation or manifest
hash, actor, timestamp, previous and new selectors, the before-and-after endpoint sets, CNP status or
conditions, and Hubble verdict counts. Track selector cardinality after deployment as well: a
one-time count goes stale the moment workloads scale or labels change.

The verdicts are already there to be counted:

```console
$ hubble observe flows -t policy-verdict --last 1
... default/tiefighter:54134 (ID:31028) -> default/deathstar:80 (ID:16530) policy-verdict:none AUDITED (TCP Flags: SYN)
... default/tiefighter:59824 (ID:31028) -> default/deathstar:80 (ID:16530) policy-verdict:L3-L4 ALLOWED (TCP Flags: SYN)
... default/xwing:54842 (ID:22654) <> default/deathstar:80 (ID:16530) policy-verdict:none DENIED (TCP Flags: SYN)
```

`AUDITED` is what a would-be drop looks like while audit mode is on, `DENIED` is the same flow once
enforcement is real, and the transition between those two strings for a given flow is the signal a
rollout would gate on if it could.

**Make rollback declarative rather than remembered.** Policy rollback is restoring a known-good
effective policy set and verifying that every intended endpoint has converged. Store the last
known-good manifest or Git commit, the exact restore command, the expected endpoint set, and the
post-rollback verification query.

Policies are Kubernetes resources, so the ecosystem already has the mechanism: keep them in Git and
let a reconciler own cluster state. Rollback becomes a `git revert`, and reconciliation restores
enforcement without anyone reconstructing what the rule used to say. It also closes the drift gap: if
someone patches a policy directly on the cluster at 3 a.m., continuous reconciliation puts it back
and tells you it did.

## The thing worth discussing

The gap is not an endpoint mode. It is **policy-scoped shadow evaluation**: the ability to apply one
candidate policy in a non-enforcing mode and observe what it alone would change, while everything
already in place keeps enforcing.

That is a genuine design problem rather than a missing flag. A real proposal would have to define
behavior across overlapping KNP, CNP, CCNP and KCNP rules, how deny precedence applies to a shadowed
policy, how verdicts are attributed to the candidate rather than the effective set, whether promotion
is atomic, and how a shadowed policy interacts with policies already enforced on the same endpoints.

It would also need guardrails, because a mechanism for leaving policy unenforced is its own hazard:
enforce by default, an audit expiry or TTL, visible status conditions, restricted RBAC and admission
control over who may shadow, and alerts for policies left in audit.

I am not claiming that design is right, or cheap. Access control has correctness requirements that
delivery tooling does not. But the closest current analogue is an endpoint-level debug flag with a
documented warning attached, which seems worth revisiting rather than inheriting.

The general pattern is one I keep meeting in different clothes: the config change that can take an
application down is often the one with the least rollout machinery around it, because it does not
look like a deployment. Policy is a change. It deserves the same question every other change gets,
which is what happens if this one is wrong.
